Self-Hosting

E.V.A is a Node.js + TypeScript application with an SQLite database. The managed host runs one Discord bot alongside its private supervisor; no external database service is required.

Requirements

  • Node.js 22.12.0 or newer (Node 22 and 24 are checked in CI)
  • Git and npm for automatic release updates
  • A Discord bot token (Developer Portal → Bot)
  • Optional: Challonge API key, Twitch app credentials

Install & run

git clone <repository>
cd ra3-eva-bot
npm ci
cp .env.example .env    # fill in DISCORD_TOKEN
npm run build
npm start

.env.example documents every variable. Only DISCORD_TOKEN is required — everything else degrades gracefully. npm run diagnose checks the configuration and reports anything missing.

Useful scripts

Script Purpose
npm run build Compile to dist/
npm run typecheck TypeScript check
npm test Test suite (vitest)

npm run seed:masters Seed the Hall of Fame list

Data

Everything is stored in a single SQLite file (data/bot.db, WAL mode). Migrations run automatically at boot. The Red Alert font for the charts lives in fonts/. Generals Evolution charts use the bundled fonts/Miedinger-Book.otf from indestructible type*. It is distributed under the SIL Open Font License in fonts/OFL-Miedinger.txt.

Automatic updates

npm start runs a private process supervisor on Windows or Linux. It restarts the current bot after /restart or a crash, with bounded retries. /kill and npm stop stop the supervisor too. There is no public update endpoint and Discord administrators cannot change the trusted repository or run hosting commands.

Updates are off by default. To enable them, add these settings to the hosting machine's .env and restart the host: 

AUTO_UPDATE_ENABLED=true
AUTO_UPDATE_INTERVAL_MINUTES=360

Only a newer, published stable release from ArcyFlame/RA3-EVA-Bot is accepted. Branch commits, drafts, prereleases and downgrades are not deployed. No GitHub token is needed. Run npm run update:check for a read-only check. Version, active commit and the latest update error are saved in .updates/state.json.

  1. The release tag's commit is resolved through GitHub, then checked against the downloaded Git commit.
  2. A separate release directory is built with the locked dependencies. Only canvas and SQLite native install scripts are enabled. The production dependency audit, build, lint and tests must pass.
  3. Migrations and native modules are rehearsed on a disposable database snapshot while the current bot remains online.
  4. The old bot stops, a final checked database backup is taken, and the candidate starts in probation. It cannot handle guild events, post or change commands yet.
  5. After successful login and a 15-second startup check, the release is activated. Startup failure restores the previous code and database; a failed commit is not retried automatically.

The checkout, local edits, .env, shared database and logs stay in place. Releases, failed staging directories and backups live in .updates/, which is private and excluded from Git. Keep it on local storage with enough disk space. Old backups and releases are retained for recovery; inspect storage occasionally and never remove the active/pending release or its rollback backup. Do not run a direct bot process alongside the managed host with the same token/database.

Automatic updates trust the repository's release maintainers and the locked npm dependencies. Commit matching is not a publisher signature and cannot protect against a compromised maintainer account. Builds do not inherit bot/API secrets, but they are not an operating-system sandbox: use a dedicated, unprivileged hosting account. Node.js, Git and operating-system security updates remain the host administrator's responsibility. Do not run automatic npm audit fix against the live installation.

Automatic database rollback is limited to provisional startup, before normal traffic is enabled. A later failure uses bounded restarts or stops for inspection; it does not rewind player data created after activation. If DATABASE_PATH changes during an update, recovery stops for manual review rather than overwriting a different database. npm run start:direct remains available without supervision or automatic updates.

Running on a Linux server

Run the supervisor as a dedicated account, with writable application storage. A systemd service can use the following template after you adjust the paths and create the eva account. Use on-failure, not always, so an intentional owner shutdown stays stopped. 

[Unit]
Description=E.V.A community bot
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=600
StartLimitBurst=3

[Service]
Type=simple
User=eva
WorkingDirectory=/opt/ra3-eva-bot
ExecStart=/usr/bin/node /opt/ra3-eva-bot/scripts/host-bot.js
Environment=NODE_ENV=production
Restart=on-failure
RestartSec=15
KillMode=control-group
TimeoutStopSec=45
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target

Native canvas/SQLite builds may need platform-specific build tools, Cairo and Pango. Updates fail closed if the server cannot build or test a release. For an immutable Docker image or read-only deployment, leave this updater disabled and update the image through your deployment platform instead.

Moving to another host

Keep the bot token and other secrets in the host's environment variables. Do not combine automatic GitHub branch pulls with this stable-release updater: an in-place git pull is not a checked release deployment. Avoid startup commands which reinstall unpinned packages on every restart. The runtime needs Git, npm, native module support and writable, persistent data/, logs/ and .updates/ directories.

Staging is skipped unless at least 1 GiB of disk and 512 MiB of RAM are available; Linux container memory limits are included. These are minimum headroom checks, not a guarantee that every future release fits. Small hosting plans may need updates built elsewhere and uploaded manually, with AUTO_UPDATE_ENABLED=false. Confirm your server's limits before relying on unattended hosting.

Stop the local bot before starting the hosted copy with the same token. Transfer the SQLite database while both copies are stopped, keep a local backup, and do not upload credentials or runtime data to GitHub. The supervisor still starts only one Discord client.

Publishing an update

Maintainers update package.json and package-lock.json to the same stable version, run the checks, tag that commit as vX.Y.Z, and publish a GitHub release. Keep updater protocol 1 compatible and set botUpdater.schemaVersion to the newest registered migration. The checked-in CI runs on pushes, tags and pull requests. Dependency security fixes are reviewed and delivered in releases, not installed into the live bot independently of its lockfile.

YouTube notifications work key-free through RSS polling. The optional PubSubHubbub push mode needs a public callback URL — see YOUTUBE_CALLBACK_BASE in .env.example.
